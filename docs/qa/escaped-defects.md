# 逃逸缺陷台账

> 目的：记录「测试全绿、用户一测就错」的缺陷，倒逼用例回灌，持续压低逃逸率。
> 规则：手工发现的缺陷，当天登记并在同一天补一条 `[BUG-xxx]` 回归用例（真实角色 + 完整 UI 路径 + 负向断言）。

## 回灌规则

1. **当天登记**：发现即建条目，不允许只修代码不写用例。
2. **真实角色**：用例必须用生产真实角色执行（`ROLE_USER` / `ROLE_LEADER` / `ROLE_WAREHOUSE` …），admin 只用于造数与清理。
3. **完整路径**：从页面入口点到出错的那一下，不能只测接口。
4. **负向断言**：不仅断言「成功」，还要断言「不出现某个错误提示 / 不返回 403」。
5. **命名可追溯**：用例标题带 `[BUG-xxx]`，与台账编号一一对应。
6. **每周统计**：逃逸率 = 手工发现缺陷数 / 本周新增用例数，目标趋近 0。

## 检查点用法

- **CP0**：BUG-001/002 必须有绿灯用例；BUG-003/004 必须已排期。
- **CP1**：所有「已闭环」条目的用例纳入全量回归。
- **CP2**：统计本周逃逸率，并在简报中列出未闭环条目。
- **CP3**：任何会改变单据状态的动作，都要同时断言「成功后的界面状态」与「失败后的可见提示」，不能只断言接口返回（见下方复盘）。
- **CP4**：列表由副本 / 视图模型驱动时，状态变更动作还要断言「触发一次列表重算后状态仍正确」，不能只断言动作后的即时显示（见 BUG-030）。
- **CP5**：审批动作后必须断言「重新打开审批信息」时的当前环节、审批轨迹与按钮显隐，不能只断言后端状态 / 轨迹落库（见 BUG-031）。

## 覆盖盲区复盘（2026-11-05，BUG-029）

全量 212 条 E2E 没拦住「点提交没反应」，不是用例被跳过或结果被忽略，而是断言口径缺两类：

1. **只验 happy path 的接口结果，不验界面状态一致性**。`[P2-23]` 覆盖「界面新增领用 → 自动提交」，只断言成功提示与审批轨迹；`[P2-24]` 覆盖「草稿 → 审批弹窗提交」，只断言 HTTP 200 与 `PROCESSING`。两条都没断言列表行里的「提交」按钮是否消失，也完全没点过表格行的「提交」按钮。
2. **不覆盖审批失败的用户可见反馈**。所有审批用例只走 200；`installGuards` 只盯请求失败与控制台错误，而本缺陷是「请求正常返回 409 → 前端抛未捕获 promise rejection」，守卫抓不到。
