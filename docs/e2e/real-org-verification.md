## 6. 例外与边界说明

1. **R2 由 `admin` 兜底**：真实人员无独立资产管理员账号，已获用户确认，见 2 节。
2. **两个部门无 R3 使用人**：`公司领导`、`财务资金部` 由本部门负责人 / 财务人员兼任提交，
   `requireInitiator` 按「创建人本人」放行，未降低审批要求。
3. **WF1 / WF9 保留角色池**：入库是仓管 / 资产管理员归口职能，盘点单跨部门，
   部门维度不成立；两者是纵向审批的产品口径明确例外，见 `docs/dept-approval.md`。
4. **维修 / 变更不改台账状态**：按现有业务口径，这两类流程只留单据与轨迹，
   资产仍为 `IN_USE`；本轮断言「状态保持」而非「状态变化」，避免把口径问题误判为缺陷。
5. **处置 / 入库的前置状态**：为验证台账联动，用例先把资产置为 `PENDING_WRITE_OFF` /
   `PENDING_INBOUND`（对应盘亏待核销、盘盈待入库），走完审批后断言 `DISPOSED` / `IDLE`；
   这属于「补录业务单据」的真实场景，清理时已整行还原。
6. **本轮不覆盖**：扫码 / 盘点终端链路（本期边界见 README）、正式盘点报告 PDF / 签字栏、
   低值资产流程、跨公司单据（另 3 家公司的 25 台资产不在本轮范围）。
