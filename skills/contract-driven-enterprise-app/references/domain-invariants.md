# 领域不变量：状态、库存、审批、派生、权限

这些口径在参考项目中由用户逐条裁决过，属于「不符合常理就不要为了形式合规硬加」的部分。改需求时先对照本文件，再决定是否要请用户重新裁决。

## 1. 先给业务动作定性

| 性质 | 例子 | 受什么约束 |
| --- | --- | --- |
| 主数据登记 / 期初导入 | 新增资产卡片、期初建账、组织档案维护 | 校验、唯一性、审计；**不要求**串审批链 |
| 业务状态流转 | 入库、派发、借出、退库、调拨、维修、变更、处置 | 必须由单据驱动、走正式审批、完结才改台账 |
| 派生动作 | 盘亏转处置、盘盈建账入库、异常转维修 | 由主单据完结时派生，独立事务，不单独发起审批链 |

判断准则：问「这是初始状态录入，还是业务状态流转」。只有后者受「必须由已完结单据驱动」约束。不要因为「缺单据」就判违规、进而提议新增审批环节。

写差距清单/规范文档时，把「目标口径」与「现状差距」分开写；已裁决项要消除全文自相矛盾的旧措辞。

## 2. 单据状态机

- 状态集：`DRAFT`（待提交）、`PROCESSING`（进行中）、`REJECTED`（已驳回）、`REVOKED`（已撤销）、`DONE`（已完结）。转换走白名单，不在白名单内一律拒绝。
- **在途 vs 终态用常量表达**：在途只含 `DRAFT / PROCESSING / REJECTED`；`REVOKED / DONE` 是终态。不要用 `status !== 'DONE'` 当在途口径。
- 终态单据是审计凭证：不删、不改、不显示在「要我处理/要我关注」的行动条，但保留在「我发起的」列表末尾，标签标明终态，操作只有「查看详情」；要重办另开新单。
- `withdraw` 撤回回 `DRAFT`，仍算在途；作废 / 终止 / 撤销三种动作统一落 `REVOKED`，界面统一显示「已撤销」，动作差异写进审批轨迹，**不新增状态编码**（会牵动契约、字典 seed 与历史数据）。
- `APPROVE_RESULT` 一类审批轨迹码不是单据状态，两者不可混用。
- 非草稿状态的改/删要被状态守卫拦住（409），前端同时置灰并提示「先撤销审批」——双端收口，不只靠 UI。

## 3. 库存三段结算

适用低值易耗的领用/退库，以及任何「审批通过才动实物」的场景：

| 状态 | 动作 |
| --- | --- |
| `DRAFT` | 不动物品 |
| `PROCESSING` | 预占 `reserved`（可用量 = `stock - reserved`） |
| `DONE` | 才真正扣减 / 回补 `stock`，并释放预占 |
| `REJECTED` / `REVOKED` | 释放预占 |

- 状态迁移的结算必须**幂等**：重复回调、撤回重提不能重复扣减或重复释放。
- 统计口径：领用/退库的数量与金额只算 `DONE`；审批中单独列为「在途」。
- 退库额度 = 已领未退（仅 `DONE` 计入）− 审批中退库占用；退库要等领用审批生效后才有额度。
- **例外要写明**：货到即入的入库单即使创建即为 `DONE`，不走审批；「领用」与「退库」是不同业务类型，不可复用同一流程种子。
- 反模式：「填单即扣库存」，它绕开统一审批链，且驳回后库存无法回滚。

## 4. 纵向审批（按归属部门解析到人）

- 审批环节的审批人类型支持：部门负责人、上级部门负责人、部门分管领导、指定用户/角色池。默认按**归属部门**解析到具体的人，而不是「持该角色的任何人都能批」。
- 归属部门优先级三方一致：单据 `deptId` → 资产 `deptId` → 创建人所属部门。有些单据表没有 `dept_id` 字段，必须回看资产。
- 缺配置的错误要点名：提交时预解析全部生效环节，解析不到审批人 → 400 并点名环节与所需角色；无权审批 → 403 且文案点名**具体的人**（不只是角色名）。
- 部门负责人/分管领导在主数据里维护，流程环节的审批人类型在流程配置里维护；迁移脚本要同时匹配 `NULL` 与空串。
- 例外（例如跨部门盘点单、明细横跨多部门，部门维度不成立）必须在设计文档里写明理由，不能默默退回角色池。
- **审批条件上下文不可信**：`hasDiff`、`amount` 等由客户端传的 `ctx` 只作提示，服务端按明细/台账实际值重算。改变这一点会动到既有金额门槛行为，需单独裁决。

## 5. 派生单据与事务边界

- 主单据完结时派生出的单据（处置单、入库单、维修/变更单）用**独立事务**创建；失败只回滚自身，不抛异常推翻主单据的终审结论。
- 送审前置阻断、完结不阻断：主单据提交时预检派生所需要素（名称、分类枚举码、数量范围、金额、位置、主数据 id），缺项返 400 并点名到明细项；完结阶段派生失败则把失败件数与根因追加到单据备注，供管理员手工补单。
- 不要把非法值静默兜底（例如数量为空兜底成 1）；不要吞异常只留一条 `log.warn`。
- 单号服务端生成，精确到毫秒或加随机后缀；名称/备注按列宽截断，避免唯一键冲突与超长报错。
- 历史数据不自动补录：可能已有关联台账，凭空派生会形成重复记录。

## 6. 盘点闭环口径

固定链路：**盘点计划 → 生成盘点单（明细取真实台账）→ 走系统正式审批链 → 按差异落账**。不允许前端自造假审批/假执行入口、假明细编号、空单送审或跳过差异环节。

- 差异由服务端按明细登记结果判定（统一读「登记结果」字段，避免与派生状态字段语义重叠）。
- 盘盈（账外资产）走入库单审批流逐件建账：建台账为待入库 + 生成 `DRAFT` 入库单，审批通过后转空闲并补入库日期。台账行承载建账要素，因为入库单契约装不下分类/部门/位置/金额。
- 盘亏在台账置「待核销」并生成 `DRAFT` 处置单；处置审批通过后转「已核销」，**保留台账行留痕不删**。
- 异常必须选处理去向（转维修 / 转变更 / 已说明），未选不得送审；「已说明」只留痕。
- 盘点单与计划是「被审计对象」：审计员只有只读权限，必须能读到盘点单，否则等于盲批；同时审批人必须有工作台待办权限，否则待办不加载。
- 明细列用 `LONGTEXT`；`TEXT` 的 64KB 上限会让全量盘点建单直接 500。
- 计划与盘点单若靠备注标记关联（契约里没有 `planId`），改这个约定必须前后端同步。

## 7. 乐观锁与并发

- 每次写操作先比对 `version`，不一致返回 409；创建时 `version=1`，更新 +1。
- 明确「请求体不带 version 时」的策略并全程一致（放行或拒绝），不要在不同接口各写一套。
- 行锁只用于需要串行化的短事务；不要用「绕过 version 的更新列」去做常规业务补丁。
- 冲突要给用户可读提示（数据已被他人修改，请刷新重试），不是 500。

## 8. 权限与数据范围

- 两层 RBAC：路由/菜单级 + 按钮/操作级；再叠加行级 `dataScope`。多角色取权限并集，停用角色不参与。
- 权限码是契约的一部分，新增权限码要同时更新权限树、角色种子、契约产物与构建期漂移检查。
- 前端隐藏按钮 ≠ 鉴权；服务端对每个写接口独立校验，默认拒绝。
- 只读角色也可能承担审批环节，检查「它有没有读到被审批对象」和「有没有待办权限」，两者缺一流程就堵死且无明显报错。

## 9. 安全底线（新系统必须一次做对）

这些是同类型老系统反复出事的通病，不因「只是内部系统」而豁免：

- 密码加盐哈希存储（BCrypt 等），绝不明文比对或明文落库；seed 明文口令只在初始化时转换为哈希。注意：若用户列表接口的响应做了脱敏，口令迁移逻辑必须使用内部未脱敏查询，否则全新部署会「没有可用账号」。
- 验证码参数必须真的校验，不能只在方法签名里接收；配合失败次数锁定与口令有效期。
- 无认证接口白名单收敛到健康检查/版本/登录；任意密码重置、用户枚举、删除资产等接口不得出现在白名单。
- 登出要真正使 token 失效（有状态 token 删记录，无状态 JWT 缩短有效期并前端丢弃）；被动登出不要再拿失效 token 调一次登出接口造成 401 死循环。
- 日志不输出 token / 口令；密钥本地强随机生成并持久化到仓库外，不入库、不进前端。
- 应用数据库账号只有 DML，DDL 由单独管理员账号执行；CORS 不回显任意 Origin 且同时 `Allow-Credentials:true`。
- 依赖版本避开已知反序列化 RCE；移除「引入了却零调用」的第三方 SDK（例如地图、人脸识别模板残留），既拖慢首屏又泄露 Key。
