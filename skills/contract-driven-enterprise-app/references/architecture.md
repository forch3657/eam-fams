# 架构规约：契约、通用引擎、双实现门面

本文件回答「改动应该从哪一层开始」。所有路径仅作为参考项目的定位示例，在新仓库中先找到同职责文件。

## 1. 契约单一真源

### 规则

- 用一份机器可读 schema 描述资源、字段、类型、可空性、枚举、引用关系、校验规则与权限码。它是唯一真源；后端契约 JSON、字典 seed、权限资源映射、API 文档都由导出脚本生成。
- 变更顺序固定：**改 schema → 运行导出 → 逐项核对产物 diff → 补迁移 SQL → 跑构建期漂移检查 → 重建部署产物**。
- 禁止直接编辑生成物。若发现生成物里有 schema 没有的字段，说明历史上有手工补丁：先把字段补回 schema 再导出，否则会被抹掉。
- 导出后必须看 diff，不只看命令成功。生成成功但字段丢失，是最隐蔽的一类缺陷。

### 为什么这条最要紧

通用引擎按契约白名单编解码，**契约未声明的字段会被静默丢弃**：不报错、不告警、测试可能全绿，只是落库少一截数据。参考项目曾因手改后端 `resources.json` 补了 8 个折旧明细列与审批目标人字段，一次导出全部冲掉，导致折旧计划明细静默缺列、加签判定读不到人。

### 演进准则

- 默认做「附加式、非破坏」变更：加可选字段、加新集合；不改已有字段语义，不复用或重排枚举码，不把「有时 null、有时缺失」混用。
- 枚举是闭集，取值必须显式；前后端枚举源同时改，只改一处会出现「取值不在枚举中」。
- 客户端做 tolerant reader（忽略不认识的字段），服务端按契约严格校验（丢弃未声明字段）。两者不矛盾，但要在文档里写清，否则前端以为字段已保存、后端其实没落库。
- 字段名、单位、时间格式在契约里写死（`amountCents` 而非 `amount`，ISO-8601 时间），避免跨模块歧义。
- 破坏性变更必须走版本化 + 迁移脚本 + 历史数据回填，不能靠「前后端一起发版」协调。

### CI 拦漂移

在唯一构建入口里串一项静态检查，至少覆盖：权限码在路由/按钮/契约/角色种子之间是否一致、枚举是否有孤儿取值、契约产物是否与 schema 同源、生成物是否被单独修改。检查失败即中止构建。

## 2. 元数据驱动通用 CRUD

### 组成

| 层 | 职责 |
| --- | --- |
| 契约加载 | 启动时把 JSON 解析成资源定义，缓存字段名、类型、枚举、引用与规则 |
| 通用 Controller | 统一路由、统一信封（code/message/data）、统一异常映射 |
| 通用 Service | 校验 → 权限 → 状态守卫 → 规则引擎 → 乐观锁 → 持久化 → Hook |
| SQL 组装 | 值一律参数占位；标识符只从契约白名单取，禁止字符串拼接列名/表名 |
| 编解码 | 按契约类型与枚举做行转换，未声明字段丢弃 |
| 规则引擎 / Hook | 声明式校验 + 状态迁移副作用（审批轨迹、快照、库存结算、限额） |
| 专用模块 | 仅承载真正复杂的业务：审批编排、折旧计算、文件导入、盘点派生 |

### 扩展点选择准则

- 能用「契约里加一条规则」解决的，不写 Hook。
- 能用「状态迁移副作用 Hook」解决的，不写专用 Controller。
- 只有满足以下任一条件才拆专用服务：跨多阶段事务、需要派生多张单据、有独立计算模型、有独立导入/导出格式。
- 不要按业务模块平铺 Controller。模块数量增长时，平铺会让同一条横切规则（权限、状态、乐观锁）出现 N 份不一致实现。

### Hook 与事务边界

- Hook 内不吞异常：业务失败要显式抛出并让用户看到，或按口径记录到单据备注。
- 派生单据用独立事务（`REQUIRES_NEW`）。留在主事务里，一次唯一键冲突会让审批动作整体回滚成 500，单据永久卡在「进行中」。
- 单号一律服务端生成，含日期 + 序号 + 随机/毫秒后缀；前端推算会跨数据范围撞唯一键。
- 大明细列用 `LONGTEXT` 一类无 64KB 限制的列类型，否则全量业务建单直接失败。

## 3. mock / api 双实现门面

### 规则

- 两套实现暴露完全相同的接口签名与返回信封；业务代码只依赖门面，不判断当前环境。
- 由环境变量 + 后端地址决定走真实接口还是 mock；回落策略要显式（例如未配置地址时回落 mock）。
- **mock 不是简化版业务**：状态机、库存结算、审批人解析、权限判定、枚举校验必须与 api 实现同口径。否则演示模式下能走通的流程，接后端后立刻崩，且问题会被误判为前端 bug。
- mock 种子必须给每个启用部门/角色配齐负责人与审批人，否则演示模式无人可审批、工作台待办为空。
- 环境标识只服务调试：mock 模式在界面显式标「演示数据」，生产界面隐藏「后端接口」等调试标签。

### 反模式

- 在组件里写 `if (useMock) { ... }` 分支。
- mock 只做列表查询、跳过审批与库存，用「假数据」掩盖口径未定。
- 用前端自造的「假审批 / 假执行」入口代替正式审批链。

## 4. 分层与数据范围

- 权限至少三层同时生效：路由 `meta.permission`、按钮 `can()`、服务端接口级校验。前端按钮隐藏只是体验，不是安全边界。
- 行级数据范围（本公司/本部门/本人）在服务端查询层统一注入，不让每个页面自己拼过滤条件。
- 「只读角色」也要能读到它要审批/抽查的对象；审批人若没有工作台待办权限，待办不加载，流程会卡死而看不出原因。
- 默认拒绝：除健康检查、版本、登录等极少数端点外全部要求认证；角色校验在服务端，不依赖前端。

## 5. 反模式速查

| 反模式 | 后果 | 正确做法 |
| --- | --- | --- |
| 手改生成物 | 下次导出抹掉，字段静默丢失 | 改 schema 再导出 |
| 按模块堆 Controller | 横切规则各写一份，逐渐分叉 | 通用引擎 + Hook |
| 契约用文档描述 | 契约与实现漂移无人发现 | 机器可读 schema + CI 校验 |
| 标识符字符串拼接 SQL | 注入面 | 值参数化 + 标识符白名单 |
| mock 只做展示 | 联调期大量「假通过」 | 同签名同规则 |
| 前端判断权限即算鉴权 | 直接调接口可越权 | 服务端默认拒绝 |
