# 交付工作流：需求采集 → 分期 → 验收 → 回灌

分期计划在这类系统里不是排期表，而是**规格**：每期写清独立验收口径、防回归清单与涉及文件，后续所有讨论以计划为准。

## 1. 需求采集清单

在写第一行代码前，把下列材料收敛成可核对的事实：

- 数据模型：集合/表、字段、类型、可空性、唯一约束、引用关系、枚举取值。优先从现有状态管理模块（Pinia store）、常量文件、契约定义与权限树里反推，而不是凭原型界面猜。
- 业务规则：状态转换白名单、互斥条件、金额/数量门槛、时效、编号规则、统计口径。
- 权限：角色清单、权限码树、数据范围、每个流程环节的审批人类型。
- 集成边界：统一认证/单点、文件导入格式、外部服务、部署形态与账号权限。
- 动作定性：逐条标注「主数据登记 / 业务流转 / 派生动作」（见 `domain-invariants.md`）。

产出物建议固定为三份：数据模型与枚举说明、业务规则与口径裁决记录、角色权限矩阵。目标口径与现状差距分开写，已裁决项要回头消除旧措辞。

**需要用户确认的开放问题**集中列出，不要边做边猜。典型项：外部统一平台如何验密码（HTTP 接口 / 直连库）、口令加密方式、用户表字段与角色映射、是否要免登、历史数据是否迁移、测试库还是生产库、清空重导由谁做。

## 2. 分期计划模板

用 `assets/phase-plan-template.md`。固定段落：

```
用户需求 → 产品概述 → 核心功能 → 约束（已与用户确认）
→ 技术栈 → 实现思路 → 分期方案（每期自带独立测试）
→ 关键实现要点（防回归）→ 目录结构 → 验收与度量 → 涉及文件清单
```

分期的通用顺序（按依赖排列，不是按业务模块排列）：

1. **P0 骨架**：工程、统一信封、异常、配置、数据库基线
2. **P1 认证与权限**：默认拒绝、口令策略、token、角色与数据范围
3. **P2 契约与通用引擎**：schema → 导出 → 通用 CRUD → 规则引擎/Hook
4. **P3 主数据**：组织、用户、字典、资产台账
5. **P4 业务主流程**：单据、审批、状态机、库存结算
6. **P5 复杂闭环**：盘点、折旧、派生单据、报表
7. **P6 系统管理与导入**：流程配置、导入导出、操作日志
8. **P7 联调与交付**：构建门禁、E2E、部署文档、验收清单

E2E 分期的执行顺序可以不同于开发顺序：先跑权限矩阵（越权是最贵的问题），再跑固定资产主流程、低值资产、审批中心，最后跑报表/导入/工作台。把顺序写进计划，不要临场决定。

每期必须写：
- 独立验收口径（怎样算这一期完成，可被别人复现）
- 防回归清单（这一期最容易破坏上一期哪些行为）
- 涉及文件清单（便于交接与评审）
- 检查点（用例清单 + 报告/截图路径 + 未预期 4xx 统计）

## 3. 检查点报告

每期结束时产出一份报告，字段固定：交付物清单、用例清单与通过数、报告/截图路径、未预期 4xx 数、遗留问题与责任人。报告是给下一期与人看的证据，不是给自己看的日志。

## 4. 缺陷回灌台账

模板见 `assets/defect-ledger-template.md`。规则：

- 当天登记，命名 `[BUG-xxx]`；写明真实角色、完整 UI 路径（从登录到出错页面）、预期与实际、根因分类。
- 每条必须补一条**负向断言**用例，让同类问题下次被自动化拦住；只修代码不补用例等于没回灌。
- 统计「逃逸率」：检查点之后才发现的缺陷占比，用来判断门禁是否失效。
- 常见根因分类：契约漂移、口径未裁决、mock 与 api 分叉、状态机漏态、事务边界、权限漏校验、编码/部署产物陈旧。

## 5. 验收度量

- 后端交付逐项核对 `assets/acceptance-checklist.md`，尤其契约、权限、状态机、乐观锁、导入、部署六节。
- 量化口径：用例 0 failed；未预期 4xx = 0（预期 4xx 必须精确到「方法 + URL」，不接受整页 403 放行）；覆盖规定的真实角色旅程；权限矩阵 100% 覆盖；覆盖率阈值达标；版本一致性提示生效。
- 用真实角色走完整链路（登录 → 建单 → 送审 → 审批 → 完结 → 台账变化 → 报表），不要用管理员账号一路到底。

## 6. 测试触发偏好（重要）

- 日常 UI / 数据展示类改动：只做必要构建确认编译通过，把验证交给用户手动点测；不主动创建临时冒烟脚本、不主动跑自动化浏览器测试。
- 生产化、加固等里程碑：用户会明确要求跑无头浏览器 E2E，此时才执行，并保留可重复的脚本与报告。
- 涉及已部署产物（前端源码 / 后端代码）的改动，按 `quality-gates.md` 的顺序重建并重启，说明站点会短暂不可用；不必等用户单独发「重新构建」指令。旧 jar/dist 会让改动完全看不到。

## 7. 后端交接包

交给后端工程师/合作方的最小集合：

1. 数据模型与枚举（含字段级校验与唯一约束）
2. 业务规则与口径裁决记录（含「已按默认实现、改动需用户明确」的项）
3. 角色权限矩阵 + 数据范围
4. API 契约与统一信封/错误码
5. 分期计划与每期验收口径
6. 部署与账号权限说明（哪些 DDL 需要管理员）
7. 缺陷台账与防回归清单

交接时明确「契约产物由谁导出、什么时机导出」，这一条不写清楚，后续必然出现手改生成物。
