# 契约驱动的企业级管理系统开发

## 定位与边界

面向「台账 + 单据 + 审批 + 库存 + 权限矩阵」形态的资产/经营管理系统，以及 Vue3/Vite/Pinia + Spring Boot/MyBatis-Plus/MySQL 这类前后端分离同构栈。提供工程决策顺序、领域不变量与验收口径，不提供业务代码模板。

适用：新增集合或字段、改审批链、改状态机、改库存语义、改权限矩阵、做导入导出、写分期计划与验收清单、做发布门禁、复盘逃逸缺陷。

不适用：纯 UI 视觉调整、单文件脚本、与单据/台账无关的通用前端页面、一次性数据修复。此类任务直接改代码即可，不必加载本 skill 的全部 references。

始终先在当前仓库定位同类实现与真源文件，再套用下列约束；不要假定目标仓库与参考项目同路径、同命名。

## 不可让渡的五条约束

1. **只改真源，不改产物**。集合定义、字段、枚举、权限码以一份机器可读 schema 为真源；后端契约 JSON、字典 seed、权限表由它导出。直接编辑产物会被下次导出抹掉，且通用引擎「丢弃契约未声明的字段」不报错，表现为数据静默少一截、测试仍全绿。
2. **先给业务动作定性，再谈流程**。区分「主数据登记/期初导入」与「业务状态流转」；只有后者才受「必须由已完结单据驱动」约束。不要为了形式合规给登记动作硬加审批环节，也不要把不同性质的动作串成一条链。
3. **状态、库存、差异、单号由服务端结算**。客户端可提交意图，不得提交结论；审批条件上下文（金额、是否有差异等）一律重算，不信任客户端传入值。
4. **横切不变量双端一致**。权限（路由 + 按钮 + 服务端）、状态机、枚举、mock 与 api 两套实现必须遵守同一套口径；mock 不是简化版业务，否则演示数据与生产行为分叉。
5. **验收以可重复证据为准，但测试触发权属于用户**。日常改动只做必要构建并交给用户手动点测；仅在用户明确要求的里程碑跑自动化 E2E。任何 E2E 代码与脚本不得自动清空业务数据。

## 固定闭环（八环）

按目标推进，而非机械执行每一步；每环结束时确认产物可验证：

1. **需求定性**：列出动作清单，逐条标注主数据登记 / 业务流转 / 派生动作；把口径裁决写进规范文档，目标口径与现状差距分开写，消除自相矛盾的旧措辞。
2. **契约**：在真源 schema 中定义资源、字段、类型、枚举、权限码与校验规则；导出产物；核对 diff；在 CI 拦漂移。设计演进时优先加可选字段，不改字段语义、不复用枚举码。
3. **引擎**：优先让一套通用 CRUD 引擎消费契约；业务差异用声明式规则、Hook 与少量专用模块注入。仅当业务含多阶段事务、复杂派生或独立计算（折旧、审批、导入）时才拆专用服务。
4. **门面**：mock 与 api 两套实现保持同一签名与同一业务规则，用环境变量切换；UI 显式标注演示数据，生产界面不出现调试标识。
5. **横切不变量**：默认拒绝的认证、两层 RBAC + 行级数据范围、状态机白名单、纵向审批、库存三段结算、乐观锁 version/409、审计留痕。
6. **分期**：用固定模板写计划，每期自带独立验收口径与防回归清单；先做权限与基础设施再做业务主流程。
7. **门禁**：唯一构建入口串行执行后端打包 → 前端单测 → 权限漂移检查 → 前端构建；CI 分层；覆盖率阈值；E2E 按既定分期顺序跑；发布前执行 `scripts/preflight.mjs`。
8. **回灌**：把逃逸缺陷按模板当天登记，补成负向断言用例，更新 `references/gotchas.md`，让同类问题不再复发。

## Gotchas 摘要

完整清单见 `references/gotchas.md`。最容易造成「改了却没生效」或「测试全绿但数据错了」的几条：

- 手工补进后端契约 JSON 的字段，会被下一次 `export:contract` 原样抹掉；通用引擎静默丢弃未声明字段。
- 只跑 `mvn test`/`npm run build` 不产生新 jar/dist；运行中的 jar 会锁住 `target`，必须先停服务再打包。
- 派生单据若留在审批主事务里，一次唯一键冲突就会把审批动作变成 500，单据卡在 `PROCESSING`。
- 终态单据是审计凭证：不删、不改、不计入「我在途」，但保留在列表末尾可查看详情。
- Windows 下新建源码/文档偶发 UTF-16LE；`.ps1` 必须 ASCII-only；导入 CSV 必须 UTF-8 BOM 且禁止用 Excel 另存。
- 应用数据库账号只有 DML 无 DDL；E2E 用例不得依赖生产库数据量，会改写数据的用例必须自己还原。

## 维护约定

每次在真实任务中使用本 skill 后，若出现新的非显然失败点，追加一条到 `references/gotchas.md`；若出现新的口径裁决，更新 `references/domain-invariants.md` 并注明裁决日期。不要把「模型本来就会」的常识写进 SKILL.md。
